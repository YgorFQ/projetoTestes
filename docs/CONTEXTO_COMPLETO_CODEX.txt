1. O QUE E O SENKOLIB
---------------------

SenkoLib e uma aplicacao web colaborativa para guardar, organizar, procurar,
visualizar, copiar e manter blocos de HTML e CSS. As duas areas de conteudo
principais sao Biblioteca e Colecoes.

Biblioteca:

- guarda layouts independentes;
- permite procurar por nome, ID e tags;
- mostra preview;
- copia HTML e CSS;
- cria, edita e exclui layouts;
- cria, edita e exclui variacoes ligadas a um layout.

Colecoes:

- guarda grupos coloridos;
- guarda colecoes associadas a grupos;
- guarda layouts internos dentro de cada colecao;
- cria, edita e exclui grupos, colecoes e layouts internos;
- impede excluir um grupo que ainda possui colecoes.

Outras features independentes existentes:

- Imagens;
- Sources;
- prototipos visuais ainda nao oficiais.

Ferramentas globais do shell:

- Criacao rapida;
- Acessos;
- Backup no GitHub;
- Senko Guide;
- Notas da equipe;
- Sessao/login;
- status de disponibilidade do Firebase.


2. PROBLEMA ORIGINAL QUE MOTIVOU A MIGRACAO
-------------------------------------------

No inicio da conversa, Biblioteca e Colecoes funcionavam usando o GitHub como
se fosse banco de dados. Criar, procurar, editar e excluir dependia de indices,
IDs, manifestos e arquivos JavaScript individuais. Isso causava varios
problemas:

- o GitHub participava do CRUD normal;
- dados e codigo ficavam misturados;
- operacoes dependiam de posicoes e IDs antigos;
- edicao colaborativa real era dificil;
- mudancas entre computadores nao apareciam imediatamente;
- a estrutura acumulava muitos arquivos com responsabilidades pouco claras.

A decisao foi migrar o CRUD para Firebase e manter GitHub somente como backup
publico e historico externo.


3. DECISAO CENTRAL DE ARQUITETURA
--------------------------------

Existem somente duas fontes de leitura validas:

1. Firestore: fonte principal, atual e editavel.
2. backup/latest: ultimo snapshot publico, somente leitura.

Nao existe terceira fonte. Arquivos antigos de secoes, manifests antigos,
indices e controladores nao podem voltar a funcionar como banco paralelo.

O GitHub nao participa de criar, editar ou excluir conteudo no uso normal.
Salvar um item escreve no Firestore. O GitHub so recebe dados quando alguem
aciona manualmente o botao de backup.


4. COMPORTAMENTO DE SALVAMENTO E TEMPO REAL
-------------------------------------------

O usuario deixou explicito que o Firebase nao deve receber escrita a cada
tecla. O comportamento acordado e implementado e:

- digitar modifica apenas o rascunho local do editor;
- clicar em Salvar inicia uma transacao Firestore;
- depois do commit, listeners Firestore entregam a mudanca para os outros
  computadores conectados;
- portanto, outra pessoa ve a alteracao automaticamente sem apertar F5;
- um editor aberto percebe quando chegou uma versao remota;
- nenhuma sobrescrita silenciosa e permitida.

O sistema usa controle otimista de concorrencia:

1. O editor guarda currentRevisionId/baseRevisionId da versao aberta.
2. Ao salvar, a transacao compara essa revisao com a atual no servidor.
3. Se forem iguais, o save pode prosseguir.
4. Se forem diferentes, outro usuario salvou primeiro.
5. O segundo save falha com conflito/aborted.
6. A interface deve preservar o rascunho e explicar que existe uma versao
   mais nova.

Presenca nao e bloqueio. Duas pessoas podem abrir o mesmo item. Realtime
Database mostra quem esta no recurso, mas Firestore e revisoes decidem se o
save ainda e valido.


5. EXCLUSAO
-----------

O usuario decidiu que exclusao pode ser direta, com confirmacao visual. Nao
foi adotada lixeira ou soft delete como comportamento do produto.

Exclusoes de recursos versionados removem tambem filhos, revisoes e reservas
de nome relacionadas. A implementacao usa exclusao em fases/lotes quando a
arvore pode ultrapassar o limite de uma unica transacao.

Um grupo de Colecoes so pode ser excluido se estiver vazio. Colecoes nunca sao
apagadas automaticamente junto com um grupo.

8. AUTENTICACAO E AUTORIZACAO
-----------------------------

Entrar com Google cria uma identidade Firebase Auth, mas nao concede edicao.
Para editar, deve existir:

workspaces/senkolib/members/{uid}

Uma conta que autentica sem esse documento gera/atualiza sua propria
solicitacao:

workspaces/senkolib/accessRequests/{uid}

Essa solicitacao fica pending e aparece para gestores na ferramenta Acessos.
A conta pendente nao pode listar solicitacoes de outras pessoas nem editar
conteudo.

Existem tres cargos internos:

OWNER

- cria, edita e exclui conteudo;
- faz backup;
- aprova editores;
- aprova administradores;
- promove outra pessoa a owner;
- altera ou remove qualquer cargo permitido pelas protecoes;
- ve solicitacoes, membros e eventos.

ADMIN

- cria, edita e exclui conteudo;
- faz backup;
- ve a area administrativa;
- aprova e gerencia editores;
- nao cria, promove, rebaixa ou remove owners;
- a implementacao atual tambem nao permite que admin conceda cargo admin.

EDITOR

- cria, edita e exclui conteudo;
- faz backup;
- nao aprova pessoas;
- nao gerencia cargos;
- nao promove outros usuarios.

VISITANTE/NAO MEMBRO

- nao le dados privados do Firebase;
- nao edita;
- pode ver backup/latest publicamente em modo somente leitura.

IMPORTANTE: cargo IAM do Google/Firebase e cargo do SenkoLib sao sistemas
separados. Tornar alguem Owner/Editor do projeto no Firebase Console nao cria
automaticamente o documento members/{uid}.

Motivo: o frontend nao deve confiar nem tentar consultar privilegios IAM do
projeto Google para autorizar o produto. As regras do SenkoLib usam documentos
do workspace.

Primeiro owner ou recuperacao quando todos os owners perderam acesso:

- uma pessoa que ainda controla o projeto Firebase entra pela Firebase CLI;
- usa scripts/admin/add-member-cli-auth.js;
- o comando npm correspondente e admin:add-member;
- o script cria o membro Firestore e os espelhos necessarios no Realtime
  Database;
- depois disso, a gestao normal volta a ser feita no modal Acessos.

Comando de referencia:

npm run admin:add-member -- \
  --workspace senkolib \
  --uid UID_DA_CONTA \
  --email email@exemplo.com \
  --name "Nome da pessoa" \
  --role owner

Nao incluir UID ou email real neste arquivo. Obter os dados no Authentication
ou na solicitacao pendente.


9. MODELO DE DADOS FIRESTORE
----------------------------

Arvore principal:

workspaces/{workspaceId}
|-- members/{uid}
|-- accessRequests/{uid}
|-- memberEvents/{eventId}
|-- groups/{groupId}
|-- bibliotecaLayouts/{layoutId}
|   |-- revisions/{revisionId}
|   `-- variants/{variantId}
|       `-- revisions/{revisionId}
|-- collections/{collectionId}
|   `-- layouts/{layoutId}
|       `-- revisions/{revisionId}
|-- nameReservations/{hash}
`-- exports/{exportId}

Workspace:

- schemaVersion descreve o modelo;
- dataVersion aumenta a cada mutacao de conteudo;
- updatedAt e updatedBy registram a ultima alteracao;
- lastGithubExportVersion, lastGithubExportAt e lastGithubCommitSha registram
  o ultimo backup concluido;
- restauracoes registram status, origem, horario e contagens.

Layouts da Biblioteca:

- IDs novos sao gerados pelo Firestore;
- kind = libraryLayout;
- name e nameKey controlam exibicao e unicidade;
- tags tem limite de 40 itens, 80 caracteres cada;
- html tem limite de 750.000 caracteres;
- css tem limite de 250.000 caracteres;
- currentRevisionId controla concorrencia;
- version e contador informativo;
- auditoria guarda criador e ultima pessoa que alterou.

Variacoes:

- ficam dentro do layout pai;
- kind = libraryVariant;
- parentId aponta para o layout;
- nome e unico apenas dentro daquele pai;
- possuem revisoes imutaveis.

Colecoes:

- ficam em collections/{collectionId};
- guardam nome, nameKey, groupId, tags, version e auditoria;
- nao possuem revisoes de HTML/CSS porque sao metadados;
- concorrencia usa version.

Layouts internos:

- ficam dentro da colecao;
- kind = collectionLayout;
- parentId e collectionId apontam para a colecao;
- possuem HTML, CSS, tags e revisoes imutaveis;
- nome e unico dentro da colecao.

Grupos:

- groupId e fornecido pela feature;
- color deve ser #rrggbb;
- grupo pode existir vazio;
- uma colecao exige grupo existente.

Reservas de nome:

- ID = SHA-256 de escopo:nameKey;
- impedem duplicidade atomicamente;
- sao atualizadas na mesma transacao do recurso.

Revisoes:

- uma revisao nova e criada em cada save de conteudo versionado;
- revisoes sao imutaveis;
- baseRevisionId registra a origem;
- revisoes antigas nao aparecem no bundle publico;
- revisoes entram no snapshot tecnico de restauracao.

Exports:

- running: backup iniciado;
- completed: commit criado, com SHA, URL e fileCount;
- failed: mensagem curta de erro;
- membros e exports nao entram no backup GitHub.

11. BACKUP MANUAL PARA GITHUB
-----------------------------

Decisao final:

- backup e manual;
- nao existe backup automatico de 30 em 30 minutos;
- nao existe GitHub Action para isso;
- nao existe Cloud Scheduler;
- nao existe Cloud Function de producao;
- qualquer membro autorizado pode clicar no botao;
- cada pessoa usa seu proprio token GitHub.

Destino fixo atual:

- owner: YgorFQ
- repo: projetoTestes
- branch: main

Esse destino fica em firebase-config.js. Configuracao antiga salva no navegador
serve apenas como fallback quando o destino nao existe no projeto. O destino
do projeto deve ter prioridade.

Token:

- e digitado em um campo password;
- fica no localStorage do navegador sob chave propria;
- nunca entra nos arquivos gerados;
- nunca entra no Firestore;
- nunca entra no commit;
- deve ser fine-grained e limitado ao repositorio, com Contents read/write;
- deve ser revogado se aparecer em screenshot, log ou conversa publica.

O backup gera duas representacoes:

backup/data/

- snapshot tecnico completo;
- JSON por documento;
- inclui revisoes necessarias para restauracao;
- nao inclui membros, solicitacoes, eventos, exports, tokens ou presenca.

backup/latest/

- bundle publico carregado pelo site;
- manifest.js;
- biblioteca.js;
- colecoes.js;
- somente estado atual;
- nao inclui revisoes antigas nem dados administrativos.

Coerencia do backup:

1. Le workspace.dataVersion.
2. Le os documentos gerenciados.
3. Le dataVersion novamente.
4. Se mudou, tenta novamente.
5. Se estabilizou, gera os arquivos.
6. Cria uma unica Git tree e um unico commit.
7. Atualiza exports e metadados do workspace.

Mensagem de commit gerada:

SenkoLib backup vN (nome da pessoa)

O fluxo foi otimizado para evitar o limite secundario do GitHub. Durante os
testes anteriores ocorreram dois erros importantes:

- NetworkError when attempting to fetch resource;
- HTTP 403 por secondary rate limit.

O comportamento atual reduz chamadas, cria a tree de uma vez, traduz 401,
403, 404 e erro de rede, e orienta aguardar quando o GitHub limita requisicoes.
Nao clicar repetidamente durante um 403 de limite.

17. ORGANIZACAO INTERNA DAS FEATURES
------------------------------------

Biblioteca e Colecoes seguem o mesmo contrato:

- register.js: composition root, registro no shell e ordem de carga;
- view.js: cria estrutura DOM;
- controllers/: eventos, modais, editores e casos de uso;
- core/: estado e invariantes em memoria, sem DOM/Firebase;
- repositories/: leitura Firebase ou leitura static;
- styles/: CSS exclusivo da feature.

Regras:

- uma feature nao chama controller interno de outra;
- comportamento neutro compartilhado sobe para shared ou infrastructure;
- repository le/converte dados e devolve unsubscribe;
- controller coordena interface e traduz erros;
- escritas de conteudo passam pelo modulo transacional comum;
- shell nao conhece layout, variacao, colecao ou caminho Firestore;
- APIs globais intencionais usam prefixo Senko.


18. CARREGAMENTO SEM BUNDLER
----------------------------

O frontend usa HTML, CSS e JavaScript direto, sem etapa obrigatoria de build.
index.html e um carregador explicito. A ordem e parte do contrato:

28. COMO DIAGNOSTICAR PROBLEMAS
-------------------------------

Tela nao abre:

- seguir ordem do index.html;
- verificar erro no console;
- conferir caminho apos a reorganizacao;
- verificar register.js da area.

Tela abre vazia:

- verificar SenkoDataMode;
- verificar window.SenkoStaticBackup;
- verificar sessao/autorizacao;
- verificar listeners e unsubscribe;
- nao inserir dados fixos no controller para esconder o erro.

Salvar falha:

- aborted: conflito de revisao;
- already-exists: reserva de nome;
- permission-denied: membro, cargo ou Security Rule;
- unavailable/deadline-exceeded: Firebase/infraestrutura;
- parent ausente: layout, colecao ou grupo pai nao existe.

Outro computador nao atualiza:

- ambos precisam usar mesmo workspace e modo Firebase;
- verificar se os dois estao autorizados;
- verificar listener do pai correto;
- verificar unsubscribe prematuro ou listener duplicado.

Backup falha:

- 401: token invalido/revogado;
- 403: permissao ou limite secundario;
- 404: owner/repo/branch ou acesso do token;
- NetworkError: conexao, bloqueador, CORS/proxy ou GitHub;
- nao repetir rapidamente durante rate limit.

GitHub Pages nao mostra dado novo:

- confirmar que backup criou commit;
- confirmar que o commit esta em main;
- aguardar deployment Pages;
- conferir caminho backup/latest;
- conferir cache/versionamento;
- lembrar que Firebase ao vivo e fallback publico sao estados diferentes.
